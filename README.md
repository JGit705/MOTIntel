# MOTIntel — UK Vehicle Reliability Intelligence

Evidence-based vehicle reliability profiles built from **42.7 million real DVSA
MOT tests**. Pick a make, model and age; get a failure probability, the specific
defects behind it, and a plain-English summary generated by Claude from the
retrieved rows — and only from those rows.

**Status:** offline pipeline, model, and serving layer complete and reproducible.
App built; live deployment pending.

---

## What it does

An applied AI system in two layers over a data-engineering pipeline:

- **Failure prediction** — a calibrated gradient-boosted classifier estimating
  the probability a given vehicle fails its next MOT.
- **Grounded explanation** — a Claude-generated summary of *what actually goes
  wrong*, constrained to defect rows retrieved from the database. The model has
  no tools, no web access, and no route to any fact outside the retrieved block.

### Model comparison (FR2.4)

Split by **date**, not randomly: trained on Jan–Sep 2025, tested on Oct–Dec.
2.1M train / 682k test rows. Test-period base failure rate 28.2%.

| Model | AUC | Brier | Calibration error |
|---|---|---|---|
| Baseline (group-by make/model/age) | 0.6743 | 0.1877 | **0.0058** |
| Logistic regression | 0.6813 | 0.1872 | 0.0173 |
| **XGBoost** | **0.6910** | **0.1846** | 0.0069 |

**The honest result: XGBoost beats a group-by by 0.017 AUC.** That is a real
but modest lift, and the group-by is actually the *best-calibrated* of the
three. Reported rather than buried, because it is the more useful finding: most
of the signal in MOT failure lives in make, model and age, and a gradient
boosting machine adds relatively little on top. A 0.99 AUC here would have
meant a leak, not a triumph.

## The interesting finding

**Failure rate rises with age — then falls.**

| Vehicle age | Tests | Failure rate |
|---|---|---|
| 0–3 years | 1,475,242 | 11.01% |
| 6–9 years | 7,465,670 | 20.91% |
| 12–15 years | 4,874,900 | 37.53% |
| **18–21 years** | 1,858,569 | **42.72%** ← peak |
| 24–27 years | 260,216 | 36.73% |
| 27–30 years | 121,698 | 33.33% |

A 28-year-old car fails less often than an 18-year-old one. This is not because
old cars become reliable — it is **survivorship bias, measurable directly in the
data**. Cars that reach 25+ years are the maintained, cherished, low-mileage
survivors; the neglected ones were scrapped a decade earlier, and a scrapped car
takes no more MOTs.

It is the single clearest demonstration of why this dataset must be read as
*tests that happened*, not as a reliability ranking.

Mileage, by contrast, is monotonic and brutal — Ford Fiesta:

| Odometer | Failure rate |
|---|---|
| 0–20k | 9.8% |
| 50–80k | 35.6% |
| 120k+ | **51.3%** |

## Architecture

```
DVSA annual ZIPs (8.5 GB, 12 monthly CSVs each)
      |
      v
[ INGEST ]      raw CSV -> DuckDB raw tables
      |
      v
[ TRANSFORM ]   resolve defect codes via lookups, derive age,
                filter to initial tests with a decided outcome
      |
      v
[ ANALYTICAL TABLE ]   35.4M rows, one per test
      |
      +-------------------+-------------------+
      v                                       v
[ MODEL ]                            [ AGGREGATE EXPORT ]
XGBoost failure classifier           1.5 MB Parquet
      |                                       |
      +-------------------+-------------------+
                          v
                [ STREAMLIT APP ]
                          |
                          v
                [ LLM LAYER ]  retrieved defect rows
                               -> Claude -> grounded summary
```

## Architectural decisions

| Decision | Reason |
|---|---|
| **DuckDB over pandas** | 42.7M test rows and 92.5M defect rows. DuckDB scans CSV/Parquet off disk and materialises only what the query needs; pandas would need the lot in RAM. The full load and transform takes 49 seconds. |
| **DuckDB over Postgres** | Single-user analytical workload, no concurrent writes, no server to run. OLAP on a laptop. |
| **Offline pipeline separated from serving** | Streamlit Community Cloud offers ~1GB RAM against a 4.2 GB database. Heavy work happens once, offline; the app ships 1.5 MB of pre-aggregated Parquet and never touches raw data. |
| **SQL retrieval, not vector search** | The data is structured and the filter is exact — make, model, age band. Embedding a defect-code table to run fuzzy similarity over it would be worse engineering than a `WHERE` clause. RAG is about grounding, not vectors. |
| **Baseline before ML** | The group-by is the benchmark. It came within 0.017 AUC of XGBoost and beat it on calibration — which is the finding, and would have been invisible without computing it first. |
| **Split by date, not randomly** | A random split puts the same vehicle's January and November tests on opposite sides and leaks the answer. |

## What the data cannot tell you

This matters more than any metric here.

- **An MOT failure is not a reliability measure.** It captures safety and
  emissions defects at one annual point. Anything that broke and was repaired
  between tests is invisible.
- **It measures owner behaviour as much as build quality.** A well-maintained
  car of a "bad" model passes; a neglected car of a "good" one fails.
- **Survivorship bias is severe and increases with age** — see the finding above.
- **Fuel type is unreliable for hybrids.** DVSA documents historic
  misclassification, partly corrected from 2022 onward.
- **No repair cost, no severity weighting.** A blown bulb and a corroded
  subframe both count as one failure.

## Data quality handling

Every filter is counted and reported, never applied silently.

| Filter | Rows removed | Share |
|---|---|---|
| Retests (RT/PL/PV) — different question | 7,140,990 | 16.71% |
| No pass/fail verdict (ABA/ABR) | 218,545 | 0.51% |
| 1971 "unknown manufacture" sentinel | 223 | 0.00% |
| Odometer zero = "no reading taken" → NULL | 326,771 | 0.76% |
| Odometer above 500,000 miles | 5,395 | 0.01% |

Defect-code lookups resolved **99.66%** of defect rows.

### Traps found in the real files

The published user guide (v5.1) describes the older yearly extracts and is
wrong about the current ones. These were all found by inspecting the data:

1. **Delimiters differ within the project.** The extracts are comma-delimited;
   the lookup tables are pipe-delimited.
2. **Quotes are backslash-escaped**, not RFC-4180 doubled — `"STREETZONE 50 2T
   12\""`. Auto-detection picks an empty quote character and the load dies on
   the first model name containing a comma.
3. **There is no odometer unit field.** The guide implies one. DVSA already
   converted km→miles from 2022 onward.
4. **`test_mileage = 0` means "no reading taken"**, not zero miles.
5. **PRS is a failure.** "Pass with Rectification at Station" means the vehicle
   entered the test failing. Counting it as a pass, and including retests,
   inflates the class-4 pass rate from 72.32% to 81.30% — a 9-point error that
   would silently corrupt every downstream number.
6. **The failure-item file carries no defect category**; categories resolve only
   through `item_detail` on a composite `rfr_id + test_class_id` join.

## Reproduction

```bash
python -m venv .venv && ./.venv/bin/pip install -r requirements.txt
# xgboost needs OpenMP on macOS: brew install libomp
```

Download from [DVSA](https://open.data.dvsa.gov.uk/mot-anonymised/index.html)
into `data/raw/`: the 2025 results and failure-item extracts, plus `lookup.zip`
(unzipped to `data/raw/lookup/`). Then:

```bash
./.venv/bin/python src/run_pipeline.py   # ingest + transform + quality report
./.venv/bin/python src/model.py          # baseline, logistic regression, XGBoost
./.venv/bin/python src/export.py         # 1.5 MB serving layer
./.venv/bin/streamlit run app/app.py
```

The LLM layer needs `ANTHROPIC_API_KEY` in `.env`. Without it the app runs and
says the summary is unavailable — it never breaks.
